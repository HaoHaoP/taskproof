# 观感卡

铁律 12–14 的细则（[`../SKILL.md`](../SKILL.md)）。写一张**结果要人用眼睛看**的卡之前读一遍 —— 布局、配色、尺寸、位置、显隐、文案都算。

这个文件要防的那件事：卡描述的是**现象**，被一个只会查「能不能编译」的机器收下，然后作为退单回到你手上。十六张卡可以全部 `verify exit=0`，同时操作者退掉其中十五张，每张一个往返。问题从来不在 worker 身上，在验收判据上。verifier 的成色等于它判据的成色，而「编译过了 + 这些 DOM 在」看不见观感。

## 1. 哪些卡算观感卡

结果要人用眼睛看的卡就是**观感卡**。结构性/逻辑性的活（解析器、查询、IO 层）不算，哪怕它在 `.vue` 文件里。一张卡两样都占（既要逻辑对又要长得对）→ 拆开：先逻辑卡，后观感卡。

这条对**每个项目**都成立，不只是那个先有了 store 的项目。一张卡需要的是**参照物**，而原型行号、既有实现行号本来就是参照物。没有 store 的项目照样发观感卡。

## 2. 一个参照物头

观感卡只带**一个参照物头**，两种写法取其一：

```
region:   header-buttons                  # 收敛预算的计数单位
口径:     /abs/path/store.md#section-heading           # 参照物是 store —— 会变
参照物:   /abs/path/prototype.html:1028-1066   # 参照物是不可变来源
```

- **`口径:`** —— 参照物住在 **store** 里：那是一份**你欠它一次回写**的文件，因为它记的是决定。用了它就必须有 `region:`。
- **`参照物:`** —— 参照物是原型、既有实现，或一张圈定过的截图（`参照物: screenshot:/abs/path.png`）。没人欠它回写，所以 `region:` 可选。

两种写法都是「绝对路径 + 锚点或行号范围」（`screenshot:` 例外，只给路径）。文件是 markdown 就按标题锚；是代码就按行号。**路径里可以有空格** —— 值取到行尾，要写说明就另起一行。

`region:` 是**一个文件 + 一个视觉区域**的稳定 slug（`header-buttons`、`grid-toolbar`）—— 不是 per 元素，也不是 per 项目。它是收敛预算计数的单位，也是停更检查的键，所以「本区域的上一张卡」必须只有一个答案。

**store 不是准入条件。** 一个项目可以永远拿原型行号发观感卡，一份 store 都不建。什么时候该建：这个区域需要把决定写下来的时候 —— 实际判据是**同一区域第二次回来**，或者操作者改了一个原型表达不了的主意。建了的话它住在该项目的其它工作材料旁边（交付仓的同级），**绝不放进交付仓**。

## 3. 发车前的检查

任一条不过就**不许发车**。**跑哪几条取决于卡带的是哪个参照物头**：

| # | 检查 | `口径:`（store） | `参照物:`（不可变来源） |
|---|---|---|---|
| 1 | 文件存在 | 跑 | 跑 |
| 2 | 锚点或行号范围解析得出来 | 跑 | 跑 |
| 3 | 它在**本区域上一张卡之后被写过** | 跑 | **不适用** |
| 4 | 它所在目录**在 git 里干净** | 跑 | **不适用** |

不可变来源的 3、4 两条报**「不适用」（n/a）而不是「通过」**：原型不会变，也没人欠它一次回写，标 pass 等于给一个毫无意义的绿灯。**不适用的检查冒充通过，与「永远不会红的检查」是同一种缺陷。**

第 3 条看着吹毛求疵，其实不是。真正的毛病不是「没有 store」，是 store **停止维护**：它一停更，下一张卡就不再引它、改回描述现象，之后每张卡都建在上一张的渲染结果上，而不是建在一份规格上。没人写的 store，比没有 store 更坏。

第 4 条管的是 store **有不止一个写者**的情况。同一个功能一旦有第二个会话在干（本来就常有 —— 这正是开多条道的原因），store 可能在你写卡的当口被改，而 mtime 分不清「我忘了把决定写回去」与「别人刚写过」。只有已提交的状态分得清：store 脏了就停手，先弄清那份改动是谁的，再引任何东西。这也正是该把 store 放进版本控制的头号理由；没放的话，这条检查会如实说明并放行。

**第 3 条在卡片真正带 `region:` 头之前是空转的。** 「本区域上一张卡」是从**已发**卡文的 `brief` 里读的，而这条规矩立起来之前发出去的卡一张都没这个头 —— 于是第 3 条一律通过，并打印「无停更可比」。那不是一条在工作的防停更闸门，别把那里的绿读成它守住了。它从第一张带 `region:` 头的卡落地那一刻才开始有意义。

检查**机制化跑，别拿眼睛看**：

```bash
python3 /absolute/path/to/taskproof/tools/check-card.py /tmp/cards/<卡号>.md
```

退出码 `0` = 发车、`1` = 不许发车、`2` = 卡文件本身读不到。脚本从卡文里读参照物头（`口径:` → store；`参照物:` → 不可变来源；`screenshot:` → 只当路径），拿锚点去那个文件里解析，并从 taskproof 账本里取「本区域上一张卡」（卡自己的 `region:` 头就在 `brief` 里，所以数据库不必改）。一个参照物头都没有的卡按非观感卡跳过。它**判不了第 2 条的后半句**「那里的文字就是卡里说的那些」—— 那一条仍是你的活。

## 4. 什么算参照物

只有四类：

- **原型行号范围** —— `prototype.html:1028-1066`；
- **既有实现的行号范围** —— `release-1.2:web/src/project/views/index/params/index.vue:1-11`；
- **已圈定的对拍页** —— 见第 7 节；
- **操作者圈过的截图** + 从它量出来的取值。

操作者自己的原话**不是**参照物，你对他原话的复述也不是。

**一卡一来源。** 当一张卡想引三个来源（这个原型管配色、那个分支管行为、现状管位置），你在**写卡之前**把它们逐条对完：拿每个元素去比每个来源，把矛盾与结论写进 store，卡里只引最后胜出的那一个。账本里最贵的那张卡，就是同时背着三个来源、结尾写「若发现矛盾先别动手」的那张 —— 那是卡的缺陷，不是安全网：它把判断甩回给 worker，而 worker 是唯一做不了这个判断的一方。

## 5. 状态真值表

观感卡带的是表，不是一段话。

| 状态 | 元素A | 元素B | 元素C |
|---|---|---|---|
| 页签1 / 查看 | 有 —— `params/index.vue:6` | 无 | 有，`right: 0` |
| 页签1 / 编辑 | 有 | 有 | 有 |
| 页签2 / 查看 | 无 | 无 | 有 |

行 = 所有可能出现过的状态（页签 × 编辑/查看 × 选中/未选 × 有数据/无数据）；列 = 元素；格 = 有/无/位置，外加决定它的那处 `file:line`。

空格就是**没定过的状态**，没定过的状态一定作为返工回来。填不出来的格子（找不到参照物）不属于「先空着」—— 它是观感题（第 7 节）。

## 6. 红绿探针

每张观感卡点名一条断言：真浏览器里跑、**修之前必须是红的**、修完绿。它量的是数，不是观感 —— 元素数、`getComputedStyle` 取值、`offsetWidth`、`elementFromPoint`、类名、`aria-expanded`、`location.hash`。

确实搬不到机器那侧的，就在卡里明写一行**「人工目视」**。诚实的缺口胜过假的检查；一条只能通过的探针就是橡皮图章。

## 7. 对拍页

**观感题** = 操作者用文字答不出来的问题 —— 他看见了才知道。三条信号任一条成立就是观感题：

- 他的回答是「参考 XX 那样」「说不太清」「你看着来」；
- 本区域已经有过一张卡被退回；
- 四类参照物一个都指不出来。

任一条成立，下一个动作就**不是发卡**，是出对拍页：整个区域一份自包含 HTML（不是一题一份），项目真实色值尺寸 1:1，状态真值表每一行都给开关，有分歧处并列 2–4 个候选。操作者圈定哪一版对；该页 + 一张截图 + 取值表进 store；之后卡指它。

由主智能体手做。一个区域一份页，比一次发卡往返便宜，而且它把一条文字通道变成了共享通道：操作者的眼睛和 worker 的代码读同一个文件，而不是读对它的描述。

这份页随后**就是这个区域的参照物**：区域有 store 就走 store 引（`口径: <store>#<小节>`），没有就直接引这份页（`参照物: <页的路径>`）。

## 8. 收敛预算

同一区域连续 3 张观感卡，根因都是「操作者退回了上一张卡的产出」→ **停止发车**。出对拍页、拿到圈定、再继续。2 太早（本来就该两轮的活会被砍断）；完全不设预算，就是让一个区域烧掉一整天。

taskproof 只存 `region:` 标签与计数；判断留在主智能体 —— 工具不负责判断什么在收敛。

## 9. 什么时候才回头看协作模式

这套纪律就是让活能继续留在 **orchestrator-subagent** 上的原因：一个派有界卡的协调者、每次从零开始的 worker、一个跑验收命令的机器 verifier，而累积的上下文放在**树**里（分支、工作区、store），不放在 worker 的 context 里。worker 因此保持可替换、可降模型、可审计；记住事情的是树。

只有一种情况值得回头考虑：worker 之间开始需要读彼此的**中间发现**（不是最终成果）才能干活，而我用手工补这个洞（cherry-pick、把上一个 worker 的发现转述进下一张卡）的成本开始占主导。那时 agent 之间的共享 store 才开始值它的钱：它把你从这段翻译里买出来，账单是并发写、重复劳动、终止条件。在那之前，这个文件就是同一个想法的更便宜的那一半。
